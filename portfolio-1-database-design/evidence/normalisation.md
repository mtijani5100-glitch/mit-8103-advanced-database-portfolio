# Portfolio 1: Database Design and Modelling
## LedgerSpring Digital Bank (LSDB) — Normalisation Explanation

**MIT 8103 Advanced Database Systems**  
**Case study:** LedgerSpring Digital Bank (LSDB) — fictional Nigerian digital bank  
**Primary database:** PostgreSQL

---

## 1. Overview

This document justifies the normal form achieved by each table in the LSDB
relational schema. The schema targets **Third Normal Form (3NF)** throughout,
with one deliberate, documented denormalisation: the `available_balance` cache
on `accounts`.

---

## 2. First Normal Form (1NF)

A table satisfies 1NF when:
- Every column contains **one atomic (indivisible) value** per row.
- There are **no repeating groups** (no multiple values crammed into a single column).
- **Every row is uniquely identifiable** (primary key exists).

### Evidence in the LSDB schema

| Table | How 1NF is satisfied |
|---|---|
| `customers` | Each row holds exactly one customer. Contact information is split into individual columns (`email`, `phone`), not stored as a comma-separated list. PK: `customer_id`. |
| `accounts` | Each row holds exactly one account. A customer with two accounts has two rows in `accounts`, not two account numbers in a single column. PK: `account_id`. |
| `transactions` | Each row holds exactly one transaction request and its outcome. Source and destination account references are separate FK columns, not an "accounts" text list. PK: `transaction_id`. |
| `ledger_entries` | Each row is **one journal line** (one side of one posting). A transfer that debits one account and credits another produces two rows, not two amounts in one row. PK: `entry_id`. |
| `idempotency_keys` | Each row holds one idempotency record. The scope and key are separate columns, not a concatenated string. PK: `idempotency_id`. |
| `audit_logs` | Each row is one audit event. Metadata that varies in structure is stored in the `event_details JSONB` column rather than as multiple nullable columns. PK: `audit_id`. |

**Violation that was avoided:** an early design sketch placed `account_numbers`
as a comma-separated TEXT field inside `customers`. That was rejected because
it would make querying a specific account impossible without string parsing
and would violate 1NF.

## 3. Second Normal Form (2NF)

A table satisfies 2NF when it is in 1NF **and** every non-key attribute depends
on the **whole** primary key (no partial dependencies). Partial dependencies
are only possible when a table has a **composite primary key**.

### Analysis per table

All six tables use a **single-column surrogate primary key** generated by
`IDENTITY`. Because there is no composite key, partial dependencies cannot
exist, so all tables trivially satisfy 2NF.

The one composite **unique** constraint (`idempotency_keys.scope + idem_key`)
acts as a candidate key but is not the primary key. Non-key columns
(`request_hash`, `transaction_id`, `created_at`) all depend on the whole
candidate key, not just the scope or just the key — so 2NF is satisfied.

**Hypothetical violation for illustration:** if `ledger_entries` used
`(transaction_id, account_id)` as its PK, and stored `c.full_name` in the
entry row, `full_name` would depend only on `account_id → customer_id → full_name`,
not on the whole composite key. That would be a partial dependency and would
violate 2NF. The schema avoids this by FK-referencing `accounts` and
`customers` instead of copying customer data into `ledger_entries`.

---

## 4. Third Normal Form (3NF)

A table satisfies 3NF when it is in 2NF **and** every non-key attribute
depends **only on the primary key**, not on any other non-key attribute
(no transitive dependencies).

### Analysis per table

#### `customers`

All non-key columns (`full_name`, `email`, `phone`, `status`, `created_at`)
describe attributes of the customer identified by `customer_id`. None depend
on another non-key column. **3NF satisfied.**

#### `accounts`

`customer_id` is a FK, not a non-key data attribute, so it does not create a
transitive dependency. `available_balance` depends on the account (`account_id`),
not on the customer (`customer_id`). `account_type` depends on the account row,
not on any other non-key column. **3NF satisfied** (subject to the balance
denormalisation documented in Section 5).

#### `transactions`

`transaction_ref`, `amount`, `status`, `currency`, `failure_reason`, and
timestamps all depend on the transaction row identified by `transaction_id`.
`source_account_id` and `destination_account_id` are FK references, not data
derived from other non-key columns. **3NF satisfied.**

#### `ledger_entries`

`entry_side`, `amount`, `currency`, `line_number`, `description`, and
`entry_timestamp` all describe the specific journal line identified by
`entry_id`. They do not depend on `transaction_id` or `account_id` as data
(those are FKs to other normalised tables). **3NF satisfied.**

#### `idempotency_keys`

`request_hash` is the hash of the request payload — a property of the
idempotency record, not of the resolved `transaction_id`. `transaction_id` is
a FK. `created_at` is a property of the record. **3NF satisfied.**

#### `audit_logs`

`actor`, `action`, `entity_type`, `entity_id`, `event_details`, and
`created_at` all describe the specific audit event identified by `audit_id`.
`transaction_id` is a nullable FK reference. No non-key column depends on
another non-key column. **3NF satisfied.**

## 5. Intentional Denormalisation: Cached Account Balance

The `available_balance` column on `accounts` is **technically a derived
value** — it could be computed from `ledger_entries` every time a balance is
needed. Storing it violates strict 3NF (the balance is a function of the
ledger, not an independent fact about the account row).

### Why it is kept

Reading a customer's balance is the most frequent operation in a banking
platform. Computing it from the ledger on every request would require an
aggregate join across an unboundedly growing `ledger_entries` table, making
balance reads progressively slower as transaction volume grows.

### How consistency is maintained

The `available_balance` is **always updated in the same database transaction**
as the corresponding ledger entries, using:

```sql
UPDATE accounts
SET available_balance = available_balance - :amount
WHERE account_id = :sender_id;
```

This `SET ... = ... - :amount` form is an **atomic guarded update**, not a
read–modify–write that could race. The posting transaction is committed only
when both the ledger entries and the balance update succeed; otherwise the
entire posting rolls back.

### Reconciliation safety net

A reconciliation query (Portfolio 2) periodically computes the ledger-derived
balance and compares it to the cached value. Any discrepancy flags the account
for investigation. This means an operational bug that corrupts the cache can
be detected and corrected without corrupting the ledger (the source of truth).

### Recovery procedure

If a discrepancy is found, the cached balance is corrected to match the
ledger-derived balance inside a controlled, audited transaction. The ledger
entries themselves are never altered.

## 6. Boyce–Codd Normal Form (BCNF) — Discussion

BCNF is a stricter version of 3NF. A table is in BCNF if, for every
functional dependency `X → Y`, `X` is a superkey.

All six LSDB tables are also in BCNF, because:
- The only non-trivial functional dependencies are those where the primary key
  determines the non-key columns.
- No non-prime attribute determines another non-prime attribute (which would
  create a non-superkey determinant).

The candidate key `(scope, idem_key)` in `idempotency_keys` is a superkey
(it uniquely identifies a row), so the functional dependency
`(scope, idem_key) → request_hash` satisfies BCNF.
